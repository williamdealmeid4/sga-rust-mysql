02
Contexto

O problema e o objetivo do projeto

O que o sistema controla

  • Cursos, disciplinas e a matriz de pré-requisitos
  • Professores, turmas e limite de vagas
  • Matrículas, notas (N1, N2, exame) e faltas
  • Fechamento de semestre e histórico do aluno
  • Usuários com perfis Coordenador e Secretário

Decisão de arquitetura

  • As regras ficam dentro do MySQL: mesmo quem acessa direto pelo Workbench não consegue gravar dado inválido
  • O Rust funciona como uma camada fina: autentica, chama procedures e devolve JSON
  • Qualquer alteração feita no site aparece na hora nas tabelas do banco
Fala: o banco é o "guardião" das regras; a aplicação só pede para ele executar as operações.

database/01_estrutura.sql
CREATE TABLE matricula (
 id_matricula INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
 id_aluno INT UNSIGNED NOT NULL,
 id_turma INT UNSIGNED NOT NULL,
 n1 DECIMAL(4,2), n2 DECIMAL(4,2), exame DECIMAL(4,2),
 faltas INT NOT NULL DEFAULT 0,
 situacao VARCHAR(30) NOT NULL DEFAULT 'Cursando',
 CONSTRAINT uq_aluno_turma UNIQUE (id_aluno,id_turma),
 CONSTRAINT fk_matricula_aluno FOREIGN KEY (id_aluno)
   REFERENCES aluno(id_aluno),
 CONSTRAINT fk_matricula_turma FOREIGN KEY (id_turma)
   REFERENCES turma(id_turma),
 CONSTRAINT ck_n1 CHECK (n1 IS NULL OR n1 BETWEEN 0 AND 10)
) ENGINE=InnoDB;
Fala: as chaves estrangeiras impedem apagar um aluno ou turma que já tenha histórico (erro 1451).

Programação no SGBD · Functions

O próprio banco calcula média e situação

database/02_programacao.sql
CREATE FUNCTION fn_calcular_media(
  p_n1 DECIMAL(4,2), p_n2 DECIMAL(4,2),
  p_exame DECIMAL(4,2))
RETURNS DECIMAL(6,4) DETERMINISTIC
BEGIN
 DECLARE v_parcial DECIMAL(6,4);
 IF p_n1 IS NULL OR p_n2 IS NULL THEN
   RETURN NULL;
 END IF;
 SET v_parcial = (p_n1 + p_n2) / 2;
 IF v_parcial >= 4 AND v_parcial < 7
    AND p_exame IS NOT NULL THEN
   RETURN (v_parcial + p_exame) / 2;
 END IF;
 RETURN v_parcial;
END

fn_situacao_valores

  • Frequência abaixo de 75% → Reprovado por Falta
  • Média parcial ≥ 7 → Aprovado
  • Média parcial < 4 → Reprovado por Nota
  • Entre 4 e 7 → Em Exame; aprova se média final ≥ 5

Outras functions

  • fn_frequencia — percentual de presença
  • fn_cr_aluno — coeficiente ponderado pela carga horária
  • fn_usuario_sessao — identifica quem está logado
Fala: como o cálculo está no banco, a situação do aluno fica correta mesmo se a nota for alterada fora do sistema.

Triggers que protegem a integridade

sp_validar_matricula (chamada pela trg_valida_vagas)
SELECT id_disciplina, vagas, encerrada, semestre
  INTO v_disc, v_vagas, v_encerrada, v_semestre
  FROM turma WHERE id_turma = p_turma
  FOR UPDATE;

IF v_encerrada THEN
  SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT = 'Turma encerrada.';
END IF;

SELECT COUNT(*) INTO v_count
  FROM matricula WHERE id_turma = p_turma;
IF v_count >= v_vagas THEN
  SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT = 'RN05: turma lotada.';
END IF;

trg_valida_vagas · BEFORE INSERT ON matricula

  • Bloqueia turma encerrada, lotada ou de outro curso
  • Exige aluno com status Ativo
  • Confere aprovação nos pré-requisitos (RN06)

trg_protege_turma · BEFORE UPDATE ON turma

  • Não deixa reduzir vagas abaixo dos matriculados
  • Com alunos, preserva disciplina, semestre e total de aulas

trg_valida_pre_requisito

  • Usa WITH RECURSIVE para impedir ciclos
Fala: o SIGNAL SQLSTATE '45000' cancela a operação e a mensagem chega até a tela do usuário.

Programação no SGBD · Auditoria

Trigger de auditoria: trg_auditoria_nota

  • Dispara AFTER UPDATE na tabela matricula
  • Compara cada campo com OLD e NEW
  • O operador <=> trata NULL corretamente (nota ainda não lançada)
  • Grava em log_nota: campo, valor antigo, valor novo, usuário e data/hora
  • Matrícula com auditoria não pode ser excluída (trg_preserva_matricula)
database/02_programacao.sql
CREATE TRIGGER trg_auditoria_nota
AFTER UPDATE ON matricula FOR EACH ROW
BEGIN
 DECLARE v_nome VARCHAR(150);
 SELECT nome INTO v_nome FROM usuario
  WHERE id_usuario = NEW.id_usuario;

 IF NOT(OLD.n1 <=> NEW.n1) THEN
  INSERT INTO log_nota(id_matricula, campo,
    valor_antigo, valor_novo, usuario, id_usuario)
  VALUES(NEW.id_matricula, 'n1',
    OLD.n1, NEW.n1, v_nome, NEW.id_usuario);
 END IF;
 -- mesmo padrão para n2, exame e faltas
END
Fala: na demonstração, lançamos uma nota no site e mostramos a linha nova em log_nota no Workbench.

Programação no SGBD · Transações

Stored Procedures com controle transacional

sp_matricular_aluno
DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN ROLLBACK; RESIGNAL; END;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
  INSERT INTO matricula(id_aluno, id_turma,
    data_matricula, id_usuario)
  VALUES(p_id_aluno, p_id_turma,
    CURRENT_DATE, p_id_usuario);
  SET v_id = LAST_INSERT_ID();
COMMIT;
  • Qualquer erro dispara ROLLBACK e devolve a mensagem
  • FOR UPDATE na turma evita estourar vagas com dois acessos simultâneos
sp_fechar_semestre (cursor)
DECLARE turmas CURSOR FOR
  SELECT id_turma FROM turma
  WHERE semestre = p_semestre
    AND encerrada = FALSE FOR UPDATE;
START TRANSACTION;
OPEN turmas;
leitura: LOOP
  FETCH turmas INTO v_turma;
  IF v_fim THEN LEAVE leitura; END IF;
  -- pendências cancelam tudo
  UPDATE turma SET encerrada = TRUE
   WHERE id_turma = v_turma;
END LOOP;
COMMIT;
Fala: no fechamento é "tudo ou nada": se uma turma tiver nota pendente, nenhuma é encerrada.

Segurança no banco

Menor privilégio e sessão validada no MySQL

database/05_permissoes.sql
CREATE ROLE IF NOT EXISTS 'sga_fbi_aplicacao';

GRANT EXECUTE ON PROCEDURE
  sga_fbi.sp_matricular_aluno
  TO 'sga_fbi_aplicacao';

GRANT SELECT ON sga_fbi.vw_boletim
  TO 'sga_fbi_aplicacao';

-- a conta da aplicação nunca recebe
-- INSERT/UPDATE/DELETE direto nas tabelas
  • O usuário sga_rust_app só tem EXECUTE nas procedures e SELECT nas views
  • No login, o banco gera um token aleatório (RANDOM_BYTES(32)) e guarda apenas o hash SHA-256 em sessao_usuario
  • sp_exigir_perfil confere a sessão e bloqueia ações exclusivas do Coordenador
  • Senhas armazenadas apenas como hash Argon2id (CHECK senha_hash LIKE '$argon2id$%')
Fala: mesmo que alguém descubra a senha da aplicação, ela não consegue apagar tabelas nem burlar as regras.

Backend em Rust · src/main.rs

Servidor HTTP com Axum e rotas REST

  • #[tokio::main] cria o runtime assíncrono
  • Lê a DATABASE_URL do arquivo .env.local
  • Abre o pool de conexões antes de aceitar requisições
  • Os arquivos da interface são embutidos no executável com include_str!
  • Servidor escuta só em 127.0.0.1:3030
src/main.rs
let repo = Repository::connect(&url).await?;
let state = Arc::new(App { repo, attempts });

let app = Router::new()
  .route("/api/login", post(login))
  .route("/api/logout", post(logout))
  .route("/api/data", get(data))
  .route("/api/records/{kind}", post(create))
  .route("/api/records/{kind}/{id}",

Backend em Rust · Autenticação

Login com Argon2id sem travar o servidor

  • 1. Busca o hash com CALL sp_CredencialLogin(?)
  • 2. Devolve a conexão ao pool antes de verificar a senha
  • 3. Verifica o Argon2id em spawn_blocking, fora das threads assíncronas
  • 4. Grava a sessão com CALL sp_LoginUsuario(?,?)
  • 5. Responde com cookie HttpOnly; SameSite=Strict
  • Limite de tentativas por login contra força bruta
src/main.rs · fn login

  let cred = sqlx::query("CALL sp_CredencialLogin(?)")
    .bind(&login)
    .fetch_optional(&mut *conn)
    .await.map_err(db_error)?;
  // ...
}; // conexão liberada aqui

let valid = tokio::task::spawn_blocking(move || {
  PasswordHash::new(&hash).is_ok_and(|parsed| {
    Argon2::default()
      .verify_password(password.as_bytes(), &parsed)
      .is_ok()
  })

Fala: o Argon2 é propositalmente lento; rodar em thread separada evita que um login segure as outras requisições.

src/mysql_repo.rs · fn db_error
pub fn db_error(e: sqlx::Error) -> ApiError {
  if let Some(db) = e.as_database_error() {
    let number = db
      .try_downcast_ref::<MySqlDatabaseError>()
      .map(|err| err.number())
      .unwrap_or(0);
    let message = match number {
      1644 => db.message().to_owned(),
      1062 => "Já existe um registro com este CPF...",
      1451 => "Este registro está vinculado...",
      // ...
    };
    return ApiError(status, message);
  }
  ApiError(SERVICE_UNAVAILABLE, "...")
}
Fala: a mensagem escrita no SIGNAL da trigger é a mesma que aparece no aviso da tela.

Backend em Rust · src/domain.rs

Regras acadêmicas espelhadas no Rust

  • result_grade repete a regra do banco para mostrar a prévia da situação antes de salvar
  • Uso de Option<f64>: nota não lançada é None, equivalente ao NULL do SQL
  • match com guardas deixa cada faixa de nota explícita
  • fn reaches faz busca em profundidade para detectar ciclos de pré-requisito
  • 5 testes unitários (cargo test) cobrem notas, matrícula e integridade
src/domain.rs · fn result_grade
let partial = n1.zip(n2).map(|(a, b)| (a + b) / 2.0);

let status = if frequency < 75.0 {
  "Reprovado por Falta"
} else {
  match partial {
    None => "Cursando",
    Some(p) if p >= 7.0 => "Aprovado",
    Some(p) if p < 4.0 => "Reprovado por Nota",
    Some(_) => match average.zip(exam) {
      None => "Em Exame",
      Some((a, _)) if a >= 5.0 => "Aprovado",
      _ => "Reprovado por Nota",
    },
  }
};
Fala: compare com a fn_situacao_valores do slide 5 — é a mesma regra, em SQL e em Rust.

Demonstração e conclusão

Sistema Web ↔ MySQL Workbench

Roteiro da demonstração

  • 1. Cadastrar um aluno no SGA e anotar o RA. As consultas prontas ficam em DEMO_CRUD_AO_VIVO.sql.
  • 2. No Workbench: SELECT * FROM sga_fbi.aluno ORDER BY id_aluno DESC;
  • 3. Lançar notas e consultar matricula e log_nota
  • 4. Tentar matricular em turma lotada e mostrar o erro da trigger
  • 5. Editar o aluno no SGA e executar novamente a consulta no Workbench

Conclusão

  • As regras de negócio ficam centralizadas no MySQL: procedures, triggers e functions
  • O Rust conecta de forma segura (TLS, pool, parâmetros) e trata os erros do banco
  • O SGA grava ao salvar. O raio no Workbench atualiza o resultado da consulta. O diagrama EER mostra a estrutura.
